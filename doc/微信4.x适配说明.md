# 微信 4.x 适配说明

> 适用版本：PC 微信 **4.0.x / 4.1.x**（本机实测 **4.1.13.65**）
> 相关代码：`wx4/` 包 + `main.py` 入口

---

## 1. 为什么老程序在最新版微信上「检测不到微信运行和登录」

老代码（`app/decrypt/get_wx_info.py`）是按 **微信 3.x** 写的，4.x 几乎每一层都变了：

| 环节 | 3.x（老代码假设） | 4.x（实际情况） | 后果 |
|---|---|---|---|
| 进程名 | `WeChat.exe` | **`Weixin.exe`** | `psutil` 里根本找不到 → 直接返回 `WeChat No Run` |
| 主模块 | `WeChatWin.dll` | **`Weixin.dll`**（且不再出现在普通模块枚举里） | 报 `WeChatWin.dll Not Found` |
| 版本偏移表 | `version_list.json`（48 个 3.x 版本） | 4.x 无此偏移体系 | 报 `微信版本不匹配` |
| 密钥定位 | 在 `WeChatWin.dll` 里搜 `iphone\0` / `android\0` 特征串 | 4.x 已无此特征串；4.1+ 改存 `com.Tencent.WCDB.Config.Cipher` 对象 | `get_key()` 永远返回 `None` |
| 数据目录 | `Documents\WeChat Files\<wxid>\Msg\*.db` | `Documents\xwechat_files\<wxid>_<4位hex>\db_storage\**` | 路径不存在 |
| 数据库 | `MicroMsg.db` / `MSG0..N.db` / `MediaMSG*.db` | `contact.db` / `message_N.db` / `media_N.db` / `session.db` … | 找不到库，`Msg` 文件夹选择直接报错 |
| 加密参数 | SQLCipher 3：HMAC-SHA1 / 64000 轮 / 保留区 48B | SQLCipher 4：HMAC-SHA512 / **256000 轮** / 保留区 **80B** | 即使拿到 key 也会解出乱码 |
| 消息正文 | `MSG.StrContent`（XML 明文） | 每会话一张 `Msg_<md5(wxid)>` 表，正文可能被 **ZSTD** 压缩 | 拿到的是二进制 |

所以「检测不到微信运行和登录」不是权限问题，而是**整套假设都过期了**。这里没有小修小补的余地，
必须按 4.x 的方式重写数据获取链路（`wx4/` 包），同时保留老代码以兼容仍在用 3.x 的环境。

## 2. 4.x 的密钥是怎么拿到的

### 2.1 内存形态

WCDB（微信自研的 SQLCipher 封装）在打开数据库时，把密钥拼成 SQLCipher 的
「raw key + 显式 salt」形式：

```
PRAGMA key = "x'<64位hex=32字节enc_key><32位hex=16字节salt>'"
```

4.1+ 不再把这段明文长期留在内存，而是放进一个配置对象：

```
全局字符串  "com.Tencent.WCDB.Config.Cipher"
   └─ 配置对象（+0x88 处是一个 blob）
        └─ blob 按固定 32 字节掩码循环异或后，就是 x'<key><salt>' 字符串
```

### 2.2 提取流程（`wx4/key.py`）

1. 用 `tasklist` 列出所有 `Weixin.exe`，按内存占用降序（主进程最大）
2. `VirtualQueryEx` 枚举可读内存区域，`ReadProcessMemory` 分块读（2 MB/块，带 overlap）
3. 全内存搜 `com.Tencent.WCDB.Config.Cipher` 字面量，得到地址集合
4. 搜 `<u64(地址)><u64(0x1F)>` 这一对 16 字节 —— 它来自 `std::string` 对象
   `{ptr, size, cap}`；命中位置 `-0x10` 就是字符串节点基址
5. 从节点读 `+0x28` 拿到配置对象指针，再读 `+0x88` 得到 `{data_ptr, data_len}`
6. 读出 blob，按固定掩码异或，正则取 `x'([0-9a-fA-F]{64,192})'`
7. 滑窗切出 `(key, salt)` 候选，用**数据库第一页的 HMAC-SHA512** 校验
8. 4.0.x 老版本回退：直接全内存搜 `x'<key><salt>'` 字面量

**校验是唯一可信判据**：命中了不代表拿到的是对的东西，必须 HMAC 对上才算。

### 2.3 实测结果（本机 4.1.13.65）

```
共发现 43 个加密数据库，41 个不同 salt
扫描进程 PID=20020 (983 MB) ...
  Config.Cipher 命中 22 个密钥（候选 125）
```

22 个是本账号的库；剩下 19 个 salt 属于同机上登录过的另一个账号，
切到那个账号重新运行即可（也可以用 `--wxid` / `--db-storage` 指定）。

### 2.4 需要注意的边界

* 微信**必须处于登录状态**（主进程内存里才有配置对象）
* 如果因为权限失败，用管理员身份运行
* 密钥文件 `wx4_keys.json` 等同账号隐私，**不要提交到仓库**（已加进 `.gitignore`）

## 3. 4.x 的数据库加密（SQLCipher 4）

| 参数 | 值 |
|---|---|
| 加密算法 | AES-256-CBC，每页独立 IV |
| 页大小 | 4096 |
| KDF | PBKDF2-HMAC-SHA512，**256000 轮**（老版本可传 passphrase，本工具直接用 raw key，跳过这步） |
| mac_key | `PBKDF2-HMAC-SHA512(enc_key, salt ^ 0x3A, 2)` |
| HMAC | HMAC-SHA512（64 字节），覆盖 `内容 || IV || LE32(页码)` |
| 保留区 | 80 字节 = IV(16) + HMAC(64) |

页布局：

```
第 1 页 : [salt 16][密文 4000][IV 16][HMAC 64]     HMAC 覆盖 [16:4032]
后续页 : [密文 4016]        [IV 16][HMAC 64]     HMAC 覆盖 [0:4032]
```

解密时第 1 页要**重建** `SQLite format 3\0` 这 16 字节头。

### WAL 增量

微信用 WAL 模式，`-wal` 里的新消息如果不合并就会丢。SQLCipher 只加密 WAL 的**数据页**，
24 字节帧头是明文，所以 `wx4/decrypt.py:merge_wal()` 直接按帧解密后写回对应对开位置。
只应用「帧 salt == 文件头 salt」的帧，否则 checkpoint 后的旧世代帧会把新页覆盖掉。

### 一致性处理

微信运行时独占 `.db`，所以流程是：**先复制快照（db + -wal + -shm）→ 再解密 → `PRAGMA quick_check` 校验 → 失败重试**。
`*_fts.db` 含 FTS5 虚拟表，`quick_check` 会误报 `SQL logic error`，这类库退化为「能读 `sqlite_master` 即算通过」。

## 4. 4.x 的数据结构与消息解析

### 4.1 库与表映射

| 数据 | 位置 |
|---|---|
| 会话列表 | `session/session.db` → `SessionTable` |
| 联系人 | `contact/contact.db` → `contact`、`stranger`、`chat_room`、`chatroom_member` |
| 消息 | `message/message_N.db` → **每会话一张 `Msg_<md5(wxid)>`**，跨分片 |
| 公众号消息 | `message/biz_message_N.db` → 同上 |
| 发送者映射 | 每个 `message_N.db` 里的 `Name2Id`（`rowid` ↔ `user_name`） |
| 语音 | `message/media_N.db` → `VoiceInfo.voice_data`（SILK BLOB，明文） |
| 文件原名 | `message/message_resource.db` |

显示名优先级：**备注 → 昵称 → 微信号 → wxid**。
（老代码里的 `Msg`/`MicroMsg`/`MediaMSG` 在 4.x 中已完全不存在。）

### 4.2 消息正文

按顺序尝试：

1. `message_content` / `compress_content` 以 `28 B5 2F FD` 开头 → **ZSTD** 解压
2. `compress_content` 是明文 → 直接用
3. 「短容器头 + UTF-8 明文 + `\x01\x00` 尾巴」的裸文本 → 剥壳
4. HTML 实体反转义（`&lt;` 等）

### 4.3 消息类型

4.x 会把类型编码成 `(subtype << 32) | base_type` 的复合值，必须先取低 32 位还原，
否则引用/红包/链接会大片变成「未知类型」——`wx4/reader.py:normalize_local_type()`。

已处理：文本 / 图片 / 视频 / 语音 / 动画表情 / 位置 / 名片 / 音视频通话 / 系统消息，
以及 `local_type=49` 的 `<appmsg>` 子类型（链接、文件、引用、合并转发、小程序、直播、红包、转账、群公告…）。

> 踩坑记录：appmsg 的字段在 `<msg><appmsg><title>` 里，**不是** `<msg>` 的直接子节点，
> 所以 XML 查找必须用 `.//title` 这种「任意深度」路径。`wx4/reader.py:_txt()` 已统一处理。

### 4.4 排序

片内 `ORDER BY sort_seq ASC, local_id ASC`，跨分片再按 `create_time` 归并。
（`local_id` 在各分片里从 1 重新计数，**不能**当全局主键用。）

## 5. 怎么用

### 5.1 命令行（推荐先跑这个验证）

```bash
# 只看环境探测结果
python -m wx4 info

# 一键：取密钥 -> 解密 -> 导出（HTML）
python -m wx4 all

# 分步
python -m wx4 key                       # 提取密钥 -> wx4_keys.json
python -m wx4 decrypt                   # 解密 -> app/DataBase/decrypted
python -m wx4 sessions                  # 列出会话
python -m wx4 show wxid_xxxx            # 终端看某个会话
python -m wx4 export -f csv             # 导出全部会话为 CSV
python -m wx4 export -f html --session wxid_xxxx
python -m wx4 media                     # 只导出图片/语音/视频/文件
python -m wx4 all -f html --media       # 连媒体一起导出
```

常用参数：

| 参数 | 说明 |
|---|---|
| `--wxid` | 指定账号（默认取最近使用的） |
| `--db-storage` | 直接指定 `db_storage` 目录 |
| `--key-file` | 密钥文件路径（默认 `wx4_keys.json`） |
| `--out-dir` | 解密输出目录（默认 `app/DataBase/decrypted`） |
| `-f/--format` | `html` / `csv` / `txt` / `json` |
| `--media` | 同时导出媒体 |
| `--no-copy-dat` | 不复制未解密的 V2 图片 |

### 5.2 图形界面

```bash
python main.py
```

`main.py` 会自动判断：检测到 4.x 数据目录就用新的导出窗口，否则回退到老的 3.x 解密界面。

新窗口按 **检测微信 → 获取密钥 → 开始解密 → 加载会话 → 导出** 五步走，支持双击预览会话、
按格式导出、一键打开导出目录。

### 5.3 输出

```
app/DataBase/decrypted/          解密后的标准 SQLite（可用任意 SQLite 工具打开）
app/DataBase/export/             导出的聊天记录 + index.html 索引页
app/DataBase/export/media/       图片 / 语音 / 视频 / 文件
wx4_keys.json                    密钥（敏感，勿外传）
```

## 6. 已知限制

| 限制 | 说明 |
|---|---|
| **V2 图片未自动解密** | 微信 4.x 的图片 `.dat` 用 V2 格式（`07 08 56 32 08 07`），AES 密钥是**每次随机会话产生、只在内存里短暂存在**，不在内存里常驻。本工具会把图片按 md5 原样导出并在 HTML 里给出链接；`wx4.media.find_dat_aes_key()` 提供了内存搜索实现，但需要该图片刚被渲染过且较慢。V1 格式（`070856310807`）会自动解密。 |
| **语音是 SILK** | 导出为 `.silk`，需要 silk-v3-decoder 之类的工具转 mp3/wav。 |
| **多账号** | 一次只处理一个账号的数据目录（默认最近使用的那个，可用 `--wxid` 切换）。 |
| **微信需登录** | 取密钥依赖运行中且已登录的微信主进程。 |
| **群昵称** | 群成员显示名用的是联系人昵称，未使用「群名片」；昵称数据在 `chat_room.ext_buffer` 的 protobuf 里，尚未解析。 |
| **实时性** | 解密是快照式；微信持续在写，`-wal` 已做增量合并，但极端情况下仍可能有极少量最新消息缺失，重跑一次 `python -m wx4 all` 即可。 |
| **朋友圈/收藏** | `sns.db` / `favorite.db` 已解密但未做导出。 |

## 7. 故障排查

| 现象 | 处理 |
|---|---|
| `未检测到微信进程 Weixin.exe` | 启动并登录微信（新版进程名是 `Weixin.exe`，不是 `WeChat.exe`） |
| `OpenProcess 失败` | 用**管理员身份**运行 |
| 密钥命中数很少 | 确认微信已登录；切换账号后重新运行；`python -m wx4 info` 看账号列表 |
| `quick_check 未通过` | 已自动重试 3 次；仍失败会跳过该库，不影响其它库 |
| 消息显示为二进制乱码 | 装 `zstandard`：`pip install zstandard` |
| 会话没有消息 | 该会话可能只有「会话条目」而消息在另一个分片；用 `python -m wx4 sessions` 看「有/无」标记 |
| 想排查某个类型为什么解析不对 | `python -X utf8 tools/debug_msg.py <解密目录> <表名片段> <条数> <类型>` |
